# Running the scorer's kernels

`harness.cu`, generated by `generate_harness.py`, performs the multiply and the select that
`CudaMatrixDotProductScorer` performs and checks what they keep against a reference computed on
the host. The select is taken from the Java rather than copied, so the two cannot drift. It
is C++ so that it runs wherever a GPU is, without the bindings or a JVM. Generate it, then
compile and run it:

```bash
python3 generate_harness.py
nvcc -DUSE_CUBLAS -gencode arch=compute_80,code=compute_80 -o harness harness.cu -lcublas
./harness
```

It prints the rows it kept against the rows the host expected, and reports `PASS` or `FAIL`.

Without `-DUSE_CUBLAS` the library multiply is replaced by one written in the harness, producing
what the `cublasSgemm` call is specified to produce. That form exercises the select alone,
which is the part that is hand written.

The scorer has not been run on a GPU, which is why `MatrixDotProductScorers` lists it after a
scorer that is always available and therefore never reaches it. This harness is what to run
first on one.
